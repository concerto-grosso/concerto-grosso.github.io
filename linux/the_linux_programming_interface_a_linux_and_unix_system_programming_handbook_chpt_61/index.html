《Linux/UNIX系统编程手册》第61章 套接字：高级主题

发表于 2026-09-09 更新于 2026-09-11 分类于 Linux 本文字数： 14k

　　顺序分组套接字结合了流套接字和数据报套接字的特性：

　　● 顺序分组套接字是面向连接，并且使用bind()、listen()、accept()和connect()建立连接。

　　● 顺序分组套接字的消息边界得到保留。每次对该套接字调用read()只会返回1条消息。当调用者提供的缓冲区无法容纳消息时，超出的字节会被丢弃。

　　● 顺序分组套接字提供了可靠通信。消息会无误、按序且不重复地被传递给对等应用程序，并且保证能够到达 (假设没有系统/应用程序崩溃或网络中断)。

　　顺序分组套接字通过调用socket()并指定标志SOCK_SEQPACKET创建。

　　从历史角度，Linux和大多数UNIX实现都不支持顺序分组套接字。但是，从内核2.6.4开始，Linux支持UNIX域顺序分组套接字。

　　在互联网域中，UDP和TCP不支持SOCK_SEQPACKET，但SCTP支持。

　　流控制传输协议 (SCTP) 的设计初衷是支持电话信令，但它也具有通用性。该协议提供了可靠的面向连接的双向传输，并保留了消息边界。SCTP的显著特性之一是支持多流，它允许在单个连接上使用多个逻辑数据流 (见RFC 3257、3268和4960)。Linux从2.6开始支持该协议。

　　Linux从2.6.14开始支持1种新的数据报协议——数据报拥塞控制协议 (DCCP)。DCCP提供了拥塞控制，但不保证数据报会可靠或按序到达 (见RFC 4336和4340)。

61.1 流套接字的部分读取和部分写入

　　在某些情况下，read()和write()传输的字节数会少于请求的字节数。当对流套接字执行I/O时，也可能出现这种部分传输。

　　当套接字中待读取的字节数少于read()调用中指定的字节数时，会出现部分读取。在这种情况下，read()只会返回实际读取的字节数。

　　当缓冲区空间不足以传输所有请求的字节，并且出现以下情况之一时，会发生部分写入：

　　● write()传输部分请求的字节后被信号处理函数中断。

　　● 当套接字以非阻塞模式 (O_NONBLOCK) 运行时，可能仅传输部分请求的字节。

　　● 当传输了部分请求的字节后，发生了异步错误。这里的异步错误指的是与应用程序调用套接字API异步发生的错误 (例如，因对等应用程序崩溃而导致TCP连接出现问题)。

　　对于以上所有情况，若缓冲区空间至少能够传输1字节，则write()会成功，并返回实际传输到输出缓冲区的字节数。

　　当发生部分I/O时，重启系统调用可能有助于完成传输 (例如，传输部分请求的字节后被信号处理函数中断)。

　　函数readn()和writen()的参数与read()和write()相同。但是，它们会循环重启这些系统调用来确保始终传输请求的字节数 (除非出错或read()遇到EOF)。

61.2 shutdown()

　　对套接字文件描述符调用close()会关闭双向通信通道的两端。有时，可能只需关闭连接的一半来让数据单向传输。系统调用shutdown()提供了该功能。

　　shutdown()可用于关闭文件描述符sockfd引用的套接字的1个或2个通道，具体取决于参数how的值，该参数可以被指定为操作之一：

　　● 操作SHUT_RD会关闭连接的读取通道。后续的读取会遇到EOF。数据仍然可以被写入到套接字。当对UNIX域流套接字执行该操作后，若对等应用程序试图写入其套接字，则它会收到信号SIGPIPE并导致错误EPIPE。该操作对TCP套接字无效。

　　● 操作SHUT_WR会关闭连接的写入通道。后续的写入会生成信号SIGPIPE并导致错误EPIPE。一旦对等应用程序读取所有待读取的数据后，它会得到EOF。对等应用程序仍然能够写入套接字。该操作允许发送EOF给对端并读取响应。ssh和rsh等程序会使用该操作。该操作是shutdown()最常用的操作，也称为套接字半关闭。

　　● 操作SHUT_RDWR会关闭连接的读取通道和写入通道。该操作等同于先执行SHUT_RD再执行SHUT_WR。

　　除了参数how的语义之外，shutdown()与close()还有另一个显著区别：无论是否存在其他引用该套接字的文件描述符，它都会关闭套接字通道 (shutdown()关闭的是打开的文件描述，而非文件描述符)。

61.3 recv()和send()

　　系统调用recv()和send()会对已连接的套接字执行I/O。它们提供了read()和write()所不具备的套接字专用功能。

　　recv()和send()的前3个参数以及返回值与read()和write()相同。第4个参数flags是控制I/O行为的位掩码。

　　recv()的参数flags可以包含以下标志中的若干个 (或运算|)：

　　● 标志MSG_DONTWAIT表示以非阻塞方式调用recv()。若没有可用数据，则导致错误EAGAIN (而非阻塞进程)。可以通过fcntl()设置套接字文件描述符的标志O_NONBLOCK来实现相同的效果，不同之处在于MSG_DONTWAIT仅对本次调用生效。

　　● 标志MSG_OOB表示接收套接字带外数据。

　　● 标志MSG_PEEK表示从套接字缓冲区获取所请求的字节的副本，但不会从该缓冲区中删除这些字节。后续的recv()和read()仍然可以重新读取这些字节。

　　● 标志MSG_WAITALL表示recv()会阻塞进程，直到接收了length字节。但是，即使指定了该标志，当recv()被信号处理函数中断、对等套接字终止连接、遇到带外数据的字节、数据报的有效载荷小于length字节或套接字出错时，接收的字节数还是会小于length。

　　SUSv3说明了MSG_DONTWAIT之外的所有标志。尽管如此，有些UNIX实现还是提供了MSG_DONTWAIT。该标志是后续添加到套接字API的，所以部分早期实现未提供该标志。

　　send()的参数flags可以包含以下标志中的若干个 (或运算|)：

　　● 标志MSG_DONTWAIT表示以非阻塞方式调用send()。若无法立即传输数据 (套接字发送缓冲区已满)，则导致错误EAGAIN (而非阻塞进程)。可以通过fcntl()设置套接字文件描述符的标志O_NONBLOCK来实现相同的效果。

　　● 标志MSG_MORE与TCP套接字一起使用可以达到与套接字选项TCP_CORK相同的效果。不同之处在于该标志仅对本次调用生效。从Linux 2.6开始，该标志可以与UDP套接字一起使用，对于连续的send()或sendto()调用，若指定了该标志，则这些调用传输的数据会被打包为单个数据报，该数据包仅在后续调用未指定该标志时才会被发送 (Linux提供了与之类似的套接字选项UDP_CORK)。Linux从2.4.4开始支持该标志。此外，该标志对UNIX域套接字无效。

　　● 标志MSG_NOSIGNAL表示向对端已被关闭的连接发送数据不会生成信号SIGPIPE，相反，send()会导致错误EPIPE。可以通过忽略该信号来达到相同的效果，不同之处在于该标志仅对本次调用生效。

　　● 标志MSG_OOB表示通过流套接字发送带外数据。

　　SUSv3仅详细说明了这些标志中的MSG_OOB。MSG_DONTWAIT仅出现在少部分UNIX实现中，而MSG_NOSIGNAL和MSG_MORE是Linux特有的。

　　这2个系统调用的手册描述了这里未介绍的其他标志。

61.4.1 sendfile()

　　sendfile()会从文件描述符in_fd引用的文件传输字节到文件描述符out_fd引用的文件。前者必须能够作为mmap()的目标，这表示它通常是常规文件。这在某种程度上限制了该系统调用的使用。后者可以是常规文件或套接字。

　　对于Linux 2.4或更低版本，out_fd可以引用常规文件。内核2.6.x的某些底层实现的调整导致该参数不再支持引用常规文件。从Linux 2.6.33开始，该参数再次支持引用常规文件。

　　若参数offset不为NULL，则它指向的值将用于指定从in_fd中传输字节的起始文件偏移量。该参数是值-结果参数。当sendfile()返回时，该参数指向的值会被设置为从in_fd传输的最后1个字节的下一个字节的偏移量。对于这种情况，该系统调用不会修改in_fd的文件偏移量。

　　若参数offset为NULL，则会从in_fd的当前文件偏移量处开始传输字节，并通过更新文件偏移量来反映已传输的字节数。

　　参数count用于指定传输的字节数。若在count字节之前遇到EOF，则仅传输可用的字节。当sendfile()调用成功时，它会返回实际传输的字节数。

　　SUSv3没有说明sendfile()。有些UNIX实现提供了该系统调用的某个版本，但其参数列表通常不同于Linux的版本。

　　Linux从2.6.17开始提供非标准系统调用splice()、vmsplice()和tee()，它们提供了sendfile()提供的功能的超集。

61.4.2 套接字选项TCP_CORK

　　为了进一步提高使用sendfile()的TCP应用程序的性能，可以启用Linux特有套接字选项TCP_CORK。

　　以web服务器将网页作为响应返回给web浏览器的请求为例，该响应由HTTP首部和有效载荷组成。前者通过write()传输，后者通过sendfile()传输。对于这种场景，通常会传输2个TCP报文段：第1个 (较小的) 报文段用于传输首部，第2个报文段用于传输有效载荷。这种方法的网络带宽利用率较低，并且可能给发送端和接收端带来不必要的工作，因为1个报文段通常足以容纳HTTP首部和有效载荷。套接字选项TCP_CORK正是为了解决网络带宽利用率低的问题。

　　当启用选项TCP_CORK后，所有输出会被缓冲在单个TCP报文段中，直到达到TCP报文段大小上限、该选项被禁用、套接字被关闭或从写入第1个被缓冲字节起经过了200毫秒 (该超时时间是为了确保被缓冲的数据会被传输，即使应用程序忘记了禁用该选项)。可以通过系统调用setsockopt()来启用或禁用该选项，以下代码展示了该选项的用法 (省略了错误检查)：

　　如前所述，send()的参数flags的标志MSG_MORE可以提供类似于选项TCP_CORK的功能，但仅限于单次调用。这未必是优势。可以启用TCP套接字的选项TCP_CORK，然后通过exec()执行会对继承的文件描述符进行输出的程序 (该程序无需知晓该选项)。相比之下，使用标志MSG_MORE需要显式修改被执行的程序的源码。

　　FreeBSD提供了类似于TCP_CORK的选项TCP_NOPUSH。

61.5 getsockname()和getpeername()

　　系统调用getsockname()和getpeername()分别会返回文件描述符sockfd引用的套接字的本地地址和对等套接字地址。

　　对于这2个系统调用，参数addr指向的套接字地址结构体用于存储结果地址，该结构体的大小和类型取决于套接字域。参数addrlen是值-结果参数，在调用前，它应该被设置为addr指向的缓冲区的大小；在调用后，它会包含实际写入到该缓冲区的字节数。

　　getsockname()会返回套接字的地址族和套接字绑定的地址。当套接字由其他程序绑定，并且套接字文件描述符会在exec()期间得到保留时，该系统调用很有用。

　　当需要获取内核为互联网域套接字执行隐式绑定时为其分配的临时端口号时，getsockname()也很有用。内核会在以下情况执行隐式绑定：

　　● 对未通过bind()绑定到地址的TCP套接字调用connect()或listen()。

　　● 第1次对未绑定到地址的UDP套接字调用sendto()。

　　● 调用bind()并将端口号指定为0。在这种情况下，bind()会为套接字指定IP地址，但内核会为其选择临时端口号。

　　getpeername()会返回流套接字连接的对等套接字的地址。当服务器需要获取已连接的客户端的地址时，该系统调用很有用。调用accept()可以获取相同的信息，但当服务器是由调用accept()的程序通过exec()启动时，服务器会继承套接字文件描述符，但accept()返回的信息已不可用。

61.6 深入了解TCP

　　上图展示了TCP报文段的格式。TCP报文段包含源端口号、目的端口号、序列号、确认号、首部长度、保留字段、控制位、窗口大小、校验和、紧急指针、选项和有效载荷。

　　源端口号和目的端口号分别是发送端和接收端的端口号。

　　序列号是TCP报文段的有效载荷的第1个字节在通过该连接沿该方向传输的数据流中的偏移量。

　　首部长度是TCP报文段首部的长度，以32位字为单位。因为该字段的长度是4位，所以首部的总长度最大可以为60字节 (15字)。接收端可以通过该字段来确定选项字段的长度和有效载荷的起始位置。

　　保留字段的长度是4位，并且必须被设置为0。

　　控制位字段的8个位从左到右依次是CWR、ECE、URG、ACK、PSH、RST、SYN和FIN。

　　● CWR是拥塞窗口减少标志。

　　● ECE是显式拥塞通知回显标志。CWR和ECE是TCP/IP显式拥塞通知 (ECN) 算法的一部分。ECN是TCP/IP中相对较新的功能 (见RFC 3168)。Linux从内核2.4开始支持ECN，需要通过在Linux特有文件/proc/sys/net/ipv4/tcp_ecn中设置非0值来启用。

　　● URG为1表示紧急指针字段会包含从发送端到接收端的数据流中紧急数据的位置。

　　● ACK为1表示确认号字段包含有效信息 (该报文段确认对端之前发送的数据)。

　　● PSH为1表示将所有接收的数据立即推送给接收进程 (见RFC 793)。

　　● RST为1表示重置连接。

　　● SYN为1表示同步序列号。在建立连接期间，双方会交换设置了该标志的报文段，以便指定在每个方向上用于传输数据的初始序列号。

　　● FIN为1表示结束数据发送。

　　当接收端发送确认报文段以指示其能够接收的数据字节数时，会使用窗口大小字段。

　　校验和的计算不仅使用报文段的首部和有效载荷，还会使用12字节的伪首部。伪首部由4字节源IP地址、4字节目的IP地址、2字节的表示整个报文段长度的值、值为6的单字节 (TCP在TCP/IP协议族中的唯一协议号) 以及值为0的单个填充字节。在校验和的计算中加入伪首部是为了让接收端再次确认传入的TCP报文段是否已到达正确的目的地 (IP没有错误地接受其他主机的数据报或将其他传输层协议的分组传递给TCP)。

　　选项字段包含用于控制TCP连接的行为的选项，其长度是可变的。

　　有效载荷字段的长度可以为0 (例如，该报文段只是确认报文段)。

61.6.1 TCP序列号和确认

　　TCP为传输的每个字节分配了逻辑序列号 (连接的2个方向都有自己的序列号)。当传输报文段时，其序列号字段会被设置为有效载荷的第1个字节在通过该连接沿该方向传输的数据流中的偏移量。这使得接收端能够将接收的报文段按正确顺序组装，并在向发送端发送确认时指示接收了哪些数据。

　　为了实现可靠通信，TCP提供了肯定确认：当成功接收报文段时，接收端会向发送端发送确认报文段 (ACK标志为1)。确认报文段的确认号字段会被设置为接收端希望接收的数据的下一个字节的逻辑序列号 (其所确认的报文段的最后1个字节的序列号加1)。

　　当发送端发送报文段时，它会设置定时器。若定时器过期之前未收到确认，则重传该报文段。

61.6.2 TCP状态机和状态转换图

　　维护TCP连接需要协调TCP连接的两端。为了降低该任务的复杂度，TCP端点被建模为状态机。这表示TCP可以处于多个固定状态之一，并根据事件 (例如，位于TCP之上的应用程序调用系统调用或来自对端的TCP报文段到达) 切换到其他状态。TCP状态如下：

　　● LISTEN表示TCP端点等待对端的连接请求。

　　● SYN_SENT表示TCP端点代表应用程序发送SYN来执行主动打开，并等待对端的响应以完成连接。

　　● SYN_RECV表示之前处于LISTEN的TCP端点已接收SYN并已响应SYN/ACK (SYN和ACK标志都为1的TCP报文段)，正在等待对端的ACK以完成连接。

　　● ESTABLISHED表示已建立与对端的连接。TCP报文段可以在连接的两端双向交换。

　　● FIN_WAIT1表示应用程序已关闭连接。TCP端点已向对端发送FIN来终止本侧连接，正在等待对端的ACK。

　　● FIN_WAIT2表示之前处于FIN_WAIT1的TCP端点已接收对端的ACK。

　　● CLOSING表示之前处于FIN_WAIT1的TCP端点已接收对端的FIN，这表示对端同时试图执行主动关闭 (换句话说，TCP两端几乎同时发送FIN，这是比较罕见的情况)。

　　● TIME_WAIT表示TCP端点在完成主动关闭后已接收FIN，这表示对端已执行被动关闭。该TCP端点会在该状态下停留固定一段时间，以确保连接可靠地终止以及在创建同一连接的新实例之前网络中的所有旧重复报文段都已过期。当这段固定时间结束后，连接会被关闭，并且相关内核资源会被释放。

　　● CLOSE_WAIT表示TCP端点已接收对端的FIN。

　　● LAST_ACK表示当应用程序执行被动关闭后，之前处于CLOSE_WAIT的TCP端点已发送FIN，正在等待对端的ACK。当接收对端的ACK后，相关内核资源会被释放。

　　FIN_WAIT1、FIN_WAIT2、CLOSING和TIME_WAIT与应用程序 (即第1个关闭本侧连接的应用程序) 执行主动关闭相关。CLOSE_WAIT和LAST_ACK与应用程序 (即第2个关闭本侧连接的应用程序) 执行被动关闭相关。

　　上述TCP状态的名称是Linux源码定义的名称，与RFC 793中的名词略有不同。

　　除了以上状态之外，RFC 793还定义了状态CLOSED，表示没有连接 (没有占用内核资源的连接)。

　　上图展示了TCP状态之间的转换 (这里仅展示了TCP状态机中比较重要的转换)。每个箭头表示可能的转换，并标有触发该转换的事件。该标签要么是应用程序的行为 (粗体)，要么是接收来自对端的报文段。当TCP端点的状态改变时，它可能向对端发送报文段。

　　在上图中，TCP客户端的常规转换路线用粗实线表示，TCP服务器的常规转换用粗虚线表示，其他箭头表示不常见的转换。根据这些转换的括号中的编号，可以发现TCP两端发送和接收的报文段彼此呈镜像关系 (当建立连接后，若执行主动关闭的是TCP服务器，则TCP服务器和客户端的转换路线可能与上图相反)。

61.6.3 TCP连接建立

　　从套接字API角度，2个套接字通过以下步骤建立连接：

　　1) 服务器调用listen()执行套接字的被动打开，然后调用accept()来等待客户端连接请求。

　　2) 客户端调用connect()执行套接字的主动打开，以便建立与服务器被动套接字的连接。

　　上图展示了建立TCP连接的步骤。这些步骤称为三次握手，因为服务器与客户端之间会传递3个报文段。

　　1) connect()调用会导致客户端向服务器发送SYN。该报文段会包含客户端初始序列号 (图中的M)。该信息是必要的，因为初始序列号不会从0开始。

　　2) 服务器必须确认客户端的SYN，并通知客户端自己的初始序列号 (图中的N)。服务器通过返回SYN和ACK标志都为1的报文段来执行这些操作 (将ACK捎带在SYN中)。

　　3) 客户端向服务器发送ACK来确认服务器的SYN。

　　前2步交换的SYN报文段的首部的选项字段可能包含用于确定连接参数的信息。

　　SYN标志会占用连接的序列号空间的1个字节。这是必要的，以便该标志被明确地确认，因为设置了该标志的报文段的有效载荷长度可能不为0。这也是为什么上图中的ACK M+1报文段确认的是SYN M报文段。

61.6.4 TCP连接终止

　　从套接字API角度，2个套接字通过以下步骤终止连接：

　　1) 连接一端的应用程序 (客户端) 执行主动关闭 (调用close())。

　　2) 连接另一端的应用程序 (服务器) 执行被动关闭 (调用close())。

　　上图展示了终止TCP连接的步骤 (默认客户端执行主动关闭)。

　　1) 执行主动关闭的close()调用会导致客户端发送FIN给服务器。

　　2) 当服务器接收FIN后，它会响应ACK。服务器后续对其套接字调用read()会得到EOF (返回0)。

　　3) 执行被动关闭的close()调用会导致服务器发送FIN给客户端。

　　4) 客户端响应ACK来确认服务器的FIN。

　　与标志SYN相同，并且出于相同的原因，标志FIN也会占用连接的序列号空间的1个字节。这也是为什么上图中的ACK M+1报文段确认的是FIN M报文段。

61.6.5 对TCP套接字调用shutdown()

　　上一节的内容默认使用的是全双工关闭，即应用程序使用close()同时关闭TCP套接字的发送和接收通道。如前所述，shutdown()只会关闭连接的单个通道 (半双工关闭)。

　　执行shutdown()的操作SHUT_WR或SHUT_RDWR会启动TCP终止序列的主动关闭，无论是否存在引用同一套接字的其他文件描述符 (一旦启动TCP终止序列，TCP端点会进入FIN_WAIT1状态，然后进入FIN_WAIT2状态，同时对端进入CLOSE_WAIT状态)。

　　当执行操作SHUT_WR后，套接字文件描述符仍然有效，并且读取通道处于打开状态，所以对端仍然可以发送数据。

　　操作SHUT_RD不适用于TCP套接字，因为大多数TCP实现没有提供其预期行为，并且该操作的效果因实现而异 (对于UNIX流套接字，当执行该操作后，若对等应用程序继续写入其套接字时，则会收到信号SIGPIPE并导致错误EPIPE)：

　　● 对于Linux等有些实现，当执行该操作后，read()会在没有待读取数据时得到EOF。但是，若对等应用程序后续向其套接字写入数据，则仍然可以通过本地套接字读取这些数据。

　　● 对于BSD等其他部分实现，该操作确实会导致后续read()调用总是返回0。但是，对于这些实现，对等应用程序仍然可以向其套接字写入数据，这些数据最终会填满数据通道，然后后续write()调用会阻塞进程。

　　总之，应该避免对可移植TCP应用程序执行操作SHUT_RD。

61.6.6 状态TIME_WAIT

　　TCP在执行主动关闭时会经历状态TIME_WAIT。该状态的存在有2个目的：

　　● 实现可靠连接终止。

　　● 等待网络的旧重复报文段过期，以防止它们被该连接的新实例接收。

　　该状态与其他状态的区别在于，导致从该状态切换到CLOSED的事件是超时。该超时时间是报文段最大生存时间 (MSL) 的2倍，MSL是TCP报文段在网络中的最大生存时间。

　　IP数据报首部的生存时间 (TTL) 字段会确保IP数据报在从源主机到目的主机的过程中，若未能在固定跳数 (经过的路由器数) 内到达，则最终会被丢弃。MSL是对IP数据报超过TTL限制所需时间的估算值。因为TTL是8位，所以其最大值是255。通常，IP数据报传输所需的跳数远小于该值。但是，由于路由器配置问题等路由器异常，IP数据报可能被困在网络循环中，直到其跳数超过限制。

　　BSD套接字实现假定MSL为30秒，Linux遵循BSD的规范。因此，Linux的TIME_WAIT的超时时间是60秒。但是，RFC 1122建议将MSL设置为2分钟，所以对于遵循该建议的实现，TIME_WAIT的超时时间是4分钟。

　　61.6.4的图有助于理解TIME_WAIT的第1个目的——实现可靠连接终止。TCP连接终止期间通常会交换4个报文段。最后1个报文段是从执行主动关闭的TCP端点到执行被动关闭的TCP端点的ACK。假设该ACK无法到达，则执行被动关闭的TCP端点最终会重传其FIN。让执行主动关闭的TCP端点在TIME_WAIT停留固定一段时间可以确保它能在这种情况下重新发送最终ACK。若执行主动关闭的TCP端点已不存在，则由于TCP协议没有该连接的任何状态信息，所以它会发送RST报文段来响应再次发送FIN的执行被动关闭的TCP端点。这解释了为什么TIME_WAIT的超时时间是MSL的2倍 (分别用于最终ACK到达对端和以防需要再次发送FIN)。

　　执行被动关闭的TCP端点无需类似于TIME_WAIT的状态，因为它是最后1次交换报文段的发起端。当发送FIN后，该端点会等待对端的ACK，并且在必要时重传FIN。

　　TCP的重传算法表示可能生成重复的报文段，由于路由决策，这些重复的报文段可能在连接关闭后到达。假设当某连接关闭后，在相同的地址和相同的端口建立了新连接，即连接的新实例。此时，TCP必须防止来自上一个实例的报文段被新实例作为有效数据接收。这是通过让某个端点处于TIME_WAIT时防止新连接建立来实现的。

61.9 套接字选项

　　套接字选项会影响套接字的行为，这里仅介绍众多套接字选项中的几个。

61.9.1 setsockopt()和getsockopt()

　　系统调用setsockopt()和getsockopt()可用于设置和检索文件描述符sockfd引用的套接字的选项。

　　参数optlen用于指定optval指向的缓冲区的字节数。

　　套接字选项与打开的文件描述相关联，所以由于dup() (或类似的系统调用) 或fork()导致的文件描述符复制会共享套接字选项。

61.9.2 套接字选项SO_REUSEADDR

　　套接字选项SO_REUSEADDR有多种用途。这里仅介绍其常用用途之一——避免错误EADDRINUSE。该错误通常出现在以下2种场景下：

　　● 之前与客户端连接的服务器因调用close()或崩溃 (例如，被信号终止) 而执行了主动关闭。这导致TCP端点停留在TIME_WAIT，直到2MSL的超时时间到期。

　　● 当服务器创建子进程后，父进程终止，而子进程继续服务客户端，所以TCP端点会继续使用服务器的知名端口。

　　无论哪种场景，未结束的TCP端点无法继续接受新连接。尽管如此，在这2种情况下，大多数TCP实现默认都会阻止将新套接字绑定到服务器的知名端口。

　　客户端通常不会出现错误EADDRINUSE，因为客户端通常使用临时端口号，该端口不是处于TIME_WAIT的端口之一。但是，当将客户端绑定到某个端口时，客户端就可能出现该错误。

61.10 accept()期间标志和选项的继承

　　对于Linux，accept()返回的已连接的套接字文件描述符不会继承监听文件描述符的以下属性：

　　● 与打开的文件描述关联的状态标志 (例如，O_NONBLOCK和O_ASYNC)，它们可以通过fcntl()的操作F_SETFL设置。

　　● 文件描述符标志 (仅包括close-on-exec标志FD_CLOEXEC)，它们可以通过fcntl()的操作F_SETFD设置。

　　● 信号驱动I/O相关的文件描述符属性，它们可以通过fcntl()的操作F_SETOWN和F_SETSIG设置。

　　另一方面，accept()返回的新文件描述符会继承通过setsockopt()设置的大部分套接字选项。

　　SUSv3没有说明accept()期间标志和选项的继承细节，并且继承规则因UNIX实现而异。值得注意的是，对于某些UNIX实现，监听套接字的打开文件状态标志会被accept()返回的新文件描述符继承。为了可移植性，应该显式地重置accept()返回的文件描述符的这些属性。

61.11 TCP与UDP

　　尽管TCP提供了UDP所不具备的可靠传输，但出于以下原因，依然可以选择UDP：

　　● 单个UDP服务器可以接收并回复来自多个客户端的数据报，而无需创建和终止与每个客户端的连接 (即使用UDP传输单条消息的开销低于使用TCP)。

　　● 对于简单的通信，UDP比TCP更快，因为它不需要建立和终止连接。在理想情况下，使用TCP交换1次请求和响应的时间是2 * RTT + SPT，其中RTT是往返时间 (发送请求和接收响应所需要的时间)，SPT是服务器处理请求所需要的时间 (对于广域网，SPT可能小于RTT)。在理想情况下，使用UDP交换1次请求和响应的时间是RTT + SPT。对于间隔较远或经过多个中间路由器的主机，RTT通常是几十毫秒。

　　● UDP套接字允许广播和多播。广播允许发送端将数据报发送到指定网络的所有主机的相同端口。多播与广播类似，但允许将数据报发送给多个指定的主机。

　　● 对于音视频传输等应用程序，即使没有TCP的可靠传输，也能正常运行。此外，TCP试图恢复丢失的报文段可能导致传输延迟过长 (流媒体传输中的延迟可能比短暂的传输流丢失更严重)。因此，这种应用程序可能更倾向于使用UDP，并采用应用程序特有的策略来处理少量的丢包。

　　对于基于UDP但需要可靠性的应用程序，必须自己实现可靠性。通常，这至少需要序列号、确认、丢包重传和重复检测。但是，若还需要流量控制和拥塞控制等高级特性，则应该选择TCP (试图在UDP上实现这些特性非常复杂，并且实现后的性能不太可能优于TCP)。

61.12 带外数据

　　带外数据是流套接字特性之一，它允许发送端将传输的数据标记为高优先级，即接收端可以在不读取中间数据的情况下获取带外数据可用的通知。telnet、rlogin和ftp等程序使用该特性来终止之前传输的命令。

　　可以通过带有标志MSG_OOB的send()和recv()调用发送和接收带外数据。当套接字收到带外数据可用的通知时，内核会向其所有者 (通常是使用套接字的进程，可以通过fcntl()的操作F_SETOWN设置) 发送信号SIGURG。

　　当带外数据与TCP套接字一起使用时，同时最多只能有1字节的数据被标记为带外数据。若发送端在接收端处理带外数据之前再次发送了1字节的带外数据，则之前未被处理的带外数据将不再被标记为带外数据。

　　带外数据被限制为1字节是套接字API的通用带外模型与其使用TCP紧急模式的具体实现不匹配的结果。TCP通过报文段首部的URG标志和紧急指针字段来指示带外数据是否存在。但是，TCP无法指示带外数据的长度，所以带外数据的长度被视为1字节。

　　对于某些UNIX实现，UNIX域流套接字也支持带外数据，但Linux不支持。

　　应该尽量避免使用带外数据，因为它在某些情况下是不可靠的。替代方法是使用1对流套接字，分别用于普通通信和高优先级通信，这种方法允许单次传输多个字节的高优先级数据，并且适用于任何域的流套接字。

61.13 sendmsg()和recvmsg()

　　系统调用sendmsg()和recvmsg()是套接字I/O系统调用中用途最广泛的。前者可以完成write()、send()和sendto()所能完成的所有操作，后者可以完成read()、recv()和recvfrom()所能完成的所有操作。此外，它们还允许执行以下操作：

　　● 执行分散-聚集I/O。与readv()和writev()相同，当使用sendmsg()对数据报套接字执行聚集输出时，只会生成单个数据报。相反，当使用recvmsg()对数据报套接字执行分散输入时，单个数据报的字节会被分散到多个用户空间缓冲区中。

　　● 传输包含域特有的辅助数据 (也称为控制信息) 的消息。辅助数据可以通过流套接字或数据报套接字传递。

　　辅助数据的用途之一是通过UNIX域套接字传递文件描述符，这里实际传递的是打开的文件描述的引用，因为接收进程使用的文件描述符号通常不同于发送进程使用的文件描述符号。

　　辅助数据的另一个用途是通过UNIX域套接字传递发送进程凭证，包括发送进程的用户ID、组ID和进程ID。发送进程可以将其用户ID和组ID指定为对应的实际ID、有效ID或保存的set-user-ID/set-group-ID (这允许接收进程认证同一主机的发送进程)。

　　SUSv3未说明传递发送进程凭证。除了Linux之外，部分现代BSD和其他UNIX实现支持该特性。

　　对于Linux，特权进程可以伪造其作为发送进程凭证传递的用户ID、组ID和进程ID。伪造这些ID分别需要能力CAP_SETUID、CAP_SETGID和CAP_SYS_ADMIN。

　　Linux 2.6.33添加了类似于recvmsg()的系统调用recvmmsg()，它允许接收多个数据报。Linux 3.0添加了类似于sendmsg()的系统调用sendmmsg()，它允许发送多个数据报。
