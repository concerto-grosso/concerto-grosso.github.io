《Linux/UNIX系统编程手册》第58章 套接字：TCP/IP网络基础

发表于 2026-07-21 更新于 2026-07-22 分类于 Linux 本文字数： 7.7k

　　互联网络 (简称互联网) 将不同的计算机网络连接起来，使所有网络上的主机能够相互通信。换句话说，互联网是由计算机网络组成的网络。术语子网络 (或子网) 用于表示组成互联网的网络之一。互联网旨在隐藏不同物理网络的细节，以便向所有连接网络的主机呈现统一的网络架构。

　　尽管人们已经设计了各种互联协议，但TCP/IP已成为主流的协议族，甚至取代了以前在局域网和广域网中常见的专用协议。术语Internet用于表示连接全球数千万台计算机的TCP/IP互联网。

　　TCP/IP源于美国国防部高级研究计划局 (ARPA，后更名为DARPA，其中D表示国防) 资助的1个项目，该项目旨在设计用于早期广域网ARPANET的计算机网络架构。20世纪80年代，人们为ARPANET设计了新的协议族，该协议族称为DARPA互联网协议族，但更常见的称呼是TCP/IP协议族 (简称TCP/IP)。

　　1983年，随着4.2BSD的发布，第1个广泛使用的TCP/IP实现出现。某些TCP/IP实现直接源自BSD源码，而其他实现 (包括Linux实现) 是从头开始开发的，以BSD源码的行为作为定义TCP/IP行为的参考标准。

　　上图展示了简单的互联网。机器tekapo是路由器 (用于将子网连接起来并在它们之间传输数据的计算机)。路由器不仅需要理解所使用的互联网协议，还需要理解其所连接的所有子网使用的数据链路层协议。

　　路由器有多个网络接口，每个接口对应其连接的1个子网。更通用的术语多宿主主机表示具有多个网络接口的主机 (不一定是路由器)。多宿主主机的每个接口有不同的网络地址 (它在所有连接的子网中都有不同的地址)。

　　本书介绍的所有互联网协议都在请求评论 (RFC) 文档中进行了定义。RFC由RFC Editor发布，该机构由国际互联网协会 (ISOC) 提供资金支持。RFC是在互联网工程任务组 (IETF) 的支持下制定的。

　　以下RFC与本书涵盖的内容特别相关：

　　● RFC 791, Internet Protocol

　　● RFC 950, Internet Standard Subnetting Procedure

　　● RFC 793, Transmission Control Protocol

　　● RFC 768, User Datagram Protocol

　　● RFC 1122, Requirements for Internet Hosts - Communication Layers

　　RFC 1122扩展 (并修正) 了之前描述TCP/IP协议的各种RFC。RFC 1122也是称为主机需求RFC的一对RFC之一，另一个是RFC 1123，它涵盖了Telnet、FTP和SMTP等应用程序。

　　与IPv6相关的RFC如下：

　　● RFC 2460, Internet Protocol, Version 6

　　● RFC 4291, IP Version 6 Addressing Architecture

　　● RFC 3493, Basic Socket Interface Extensions for IPv6

　　● RFC 3542, Advanced Sockets API for IPv6

　　很多RFC和论文都对原始TCP规范进行了改进和扩展：

　　● Congestion Avoidance and Control. V. Jacobsen, 1988

　　● RFC 1323, TCP Extensions for High Performance. V

　　● RFC 2018, TCP Selective Acknowledgment Options

　　● RFC 2581, TCP Congestion Control

　　● RFC 2861, TCP Congestion Window Validation

　　● RFC 2883, An Extension to the Selective Acknowledgement (SACK) Option for TCP

　　● RFC 2988, Computing TCP's Retransmission Timer

　　● RFC 3168, The Addition of Explicit Congestion Notification (ECN) to IP

　　● RFC 3390, Increasing TCP's Initial Window

58.1 网络协议和网络层

　　网络协议是多个定义信息如何在网络上传输的规则。网络协议通常会被组织为一系列层，所有层都在其下层的基础上构建，添加可供上层使用的特性。

　　TCP/IP协议族是分层网络协议。它包括网际协议 (IP) 以及位于其之上的各种协议层 (实现各层的代码通常称为协议栈)。术语TCP/IP源于事实：TCP是使用最广泛的传输层协议。

　　上图省略了很多其他TCP/IP协议，因为它们与本章无关。地址解析协议 (ARP) 负责将互联网地址转换为硬件 (以太网) 地址。互联网控制消息协议 (ICMP) 负责在网络中传输错误和控制信息 (程序ping和traceroute基于该协议)。互联网组管理协议 (IGMP) 用于支持IP数据报多播的主机和路由器。

　　原始套接字 (SOCK_RAW) 允许应用程序直接通过网络层通信。

　　赋予协议分层强大功能性和灵活性的理念之一是透明性。所有协议层都保护上层免受下层操纵和复杂性的影响。因此，仅使用TCP的应用程序只需要使用标准套接字API，并知道它使用的是可靠的字节流传输服务 (无需知道TCP的细节)。同样，应用程序也无需知道IP或数据链路层的细节。从应用程序角度，这就像它们是通过套接字API直接通信一样，如上图所示，其中虚线表示2个主机上对应的应用程序、TCP和IP实体之间虚拟通信路径。

　　封装是分层网络协议的重要原则之一。上图展示了TCP/IP协议层封装的示例 (这里没有显示的是，封装的概念延伸到了数据链路层，IP数据报会被封装到网络帧。封装还可以延伸到应用层，应用程序可能封装自己的分组)。

　　封装的关键思想在于从上层传递给下层的信息会被下层视为不透明数据。换句话说，下层不会解析来自上层的数据，只会将其封装到下层使用的分组中，然后添加下层特有的分组首部，最后将该分组传递给下层的下层。当从下层传递信息给上层时，会发生相反的解包过程。

58.2 数据链路层

　　数据链路层由设备驱动程序和到底层物理媒介 (电话线、同轴电缆或光纤电缆) 的网络接口 (网卡) 组成。数据链路层负责在网络的物理链路上传输数据。

　　为了传输数据，数据链路层会将IP数据报封装成帧。除了待传输的数据之外，帧还包含首部 (包括目标地址和帧大小)。数据链路层通过物理链路传输帧并处理来自接收端的确认 (并非所有数据链路层都使用确认机制)。该层会执行错误检测、重传和流控制。有些数据链路层会将大型网络分组拆分为多个帧，并在接收端将其重新组装。

　　从应用程序编程角度，可以忽略数据链路层，因为所有通信细节由驱动程序和硬件处理。

　　对于IP，数据链路层的重要特征之一是最大传输单元 (MTU)。MTU是数据链路层对帧大小施加的限制。不同数据链路层的MTU不同。

　　命令netstat -i会列出系统的网络接口及其MTU。

58.3 IP

　　在数据链路层之上是网络层，网络层负责将分组从源主机传输到目的主机。该层执行多种任务：

　　● 将数据分片为足够小的报文段，以便通过数据链路层传输 (若有必要)。

　　● 在互联网中路由数据。

　　● 为传输层提供服务。

　　TCP/IP协议族中的主要网络层协议是IP。4.2BSD实现中出现的是IP第4版 (IPv4)。20世纪90年代早期，IP的修订版IP第6版 (IPv6) 出现了。这2个版本最显著的区别是IPv4通过32位地址标识子网和主机，而IPv6使用了128位地址。IPv4和IPv6都支持UDP和TCP (以及很多其他传输层协议)。

　　尽管32位地址理论上允许分配数十亿个IPv4网络地址，但由于地址的结构和分配方式，实际可用的地址少得多。IPv4地址即将耗尽是创建IPv6的主要动机之一。

　　IPv4和IPv6的存在不禁让人产生疑问：IPv5存在吗？实际上从未存在过IPv5。所有IP数据报首部都包含4位的版本号字段 (IPv4数据报的该字段总是为4)，而版本号5被分配给了实验性协议互联网流协议 (该协议的第2版简称为ST-II，RFC 1819描述了ST-II)。互联网流协议是面向连接的协议，最初构思于20世纪70年代，旨在支持音视频传输以及分布式仿真。因为IP数据报版本号5已被分配，所以IPv4的后继版本被分配了版本号6。

58.3.1 IP传输数据报

　　IP以数据报的形式传输数据。在2个主机之间的所有数据报都会独立地在网络中传输，并且可能使用不同的路由。所有IP数据报都包含首部，首部的大小在20到60字节之间。首部包含目的主机地址，以便数据报能够通过网络路由到目的主机；同时还包含发送分组的源主机地址，以便接收主机能够知道数据报的来源。

　　IP实现可以为其支持的数据报大小设置上限。所有IP实现都必须允许数据报大小不小于IP最小重组缓冲区大小所指定的限制。对于IPv4，该限制为576字节；对于IPv6，该限制为1500字节。

　　IP是无连接的，因为它未提供连接主机的虚拟线路的概念。IP是不可靠的，它会尽量将数据报从发送端传输到接收端，数据报可能乱序或重复到达，甚至根本无法送达。此外，IP没有提供错误恢复 (首部错误的数据报会被静默丢弃)。可靠性必须由可靠的传输层协议 (例如，TCP) 或应用程序本身提供。

　　IPv4提供了IP首部校验和，以允许检测首部中的错误，但没有提供有效载荷的错误检测。IPv6没有提供首部校验和，依赖上层协议提供错误检测和所需的可靠性 (IPv4中UDP校验和是可选的，但通常启用；IPv6中UDP校验和是强制性的。TCP校验和在IPv4和IPv6中都是强制性的)。

　　由于某些数据链路层为确保可靠而采用的技术，或者当IP数据报通过某些使用重传的非TCP/IP网络进行隧道传输时，可能导致IP数据报重复。

58.3.2 IP数据报分片

　　IPv4数据报最大可达65535字节。在默认情况下，IPv6允许最大65575字节 (40字节用于首部，65535用于有效载荷)，并且提供了更大的数据报选项 (即巨型数据报)。

　　大多数数据链路层都对帧大小设置了上限 (MTU)。以太网网络架构的MTU通常为1500字节。IP还定义了路径MTU，这是从源到目的路径上所有数据链路层的最小MTU (实际上，以太网MTU通常是路径中的最小MTU)。

　　当IP数据报大于MTU时，IP会将数据报分片为适合在网络中传输的单元。这些分片后的数据报 (偏移字段表示该数据报在原始数据报中的位置) 会在最终目的主机重新组装为原始数据报。

　　IP分片对上层协议是透明的，但通常被认为是不理想的。问题在于，由于IP不执行重传，并且数据报只有在所有分片都到达目的主机后才能重新组装，所以当其中的分片丢失或包含传输错误时，整个数据报将无法使用。在某些情况下，这可能导致严重的数据丢失 (对于UDP等不执行重传的上层协议) 或传输速率下降 (对于TCP等执行重传的上层协议)。现代TCP实现采用算法 (路径MTU发现) 来确定主机之间的路径MTU，并相应地对传递给IP的数据进行拆分，从而避免要求IP传输超过该大小的数据报。UDP则没有提供这种机制。

58.4 IP地址

　　IP地址由网络ID和主机ID组成。前者指定主机所在的网络，后者用于在该网络中标识主机。

58.4.1 IPv4地址

　　IPv4地址由32位组成。当以人类可读的形式表示时，这些地址通常以点分十进制表示法表示，地址的4个字节以十进制数字表示，并用点分隔 (例如，204.152.189.116)。

　　当某个组织为其主机申请IPv4网段时，它会收到32位网络地址和对应的32位网络掩码。当以二进制表示网络掩码时，左侧是若干个1，右侧是若干个0。1表示地址的哪一部分是网络ID，0表示地址的哪一部分可供组织分配为网络上的唯一主机 ID。掩码的网络ID部分的大小在分配地址时确定。由于网络ID部分始终在掩码的左侧，所以以下表示法足以指定分配的网段：

　　这里的/24表示分配的地址中的网络ID部分由左侧24位组成，右侧8位指定主机ID。该网络地址范围对应的网络掩码的点分十进制表示法为255.255.255.0。

　　持有该网段的组织可以为其计算机分配254个唯一互联网地址 (从204.152.189.1到204.152.189.254)。2个地址不能被分配：主机ID全为0的地址用于标识该网络，而主机ID全为1的地址是子网广播地址。

　　特定IPv4地址有特殊意义。地址127.0.0.1通常被定义为环回地址，并被分配给主机名localhost。实际上，网段127.0.0.0/8中的所有地址可以作为环回地址，但127.0.0.1是通常的选择。发送给环回地址的数据报永远不会到达网络，而是自动环回，成为发送主机的输入。当在同一主机上测试客户端和服务器时，该地址很有用。对于C程序，整数常量INADDR_LOOPBACK定义了该地址。

　　常量INADDR_ANY是IPv4通配地址。当运行在多宿主主机的应用程序仅将套接字绑定到主机的1个IP地址时，套接字只会收到发送到该IP地址的UDP数据报或TCP连接请求。但是，运行在多宿主主机的应用程序通常需要接收其主机的所有IP地址的数据报和连接请求，这可以通过将套接字绑定到通配IP地址来实现。SUSv3没有说明IPv4通配地址的具体值，但大多数实现都将其定义为0.0.0.0。

　　通常，IPv4地址会被划分为子网。子网划分会将IPv4地址的主机部分划分为2部分：子网ID和主机ID (主机ID如何划分由局域网管理员决定)。划分子网的原因是组织通常不会将所有主机都连接到同一网络。相反，组织通常会构建多个子网，每个子网由网络ID和子网ID的组合标识。这种组合通常称为扩展网络ID。在子网内，子网掩码的作用等同于网络掩码 (可以使用类似的表示法来表示分配给特定子网的网段)。

　　假设分配给某个组织的网段是204.152.189.0/24，该组织可以选择将8位的主机ID拆分为4位的子网ID和4位的主机ID，从而对该网段进行子网划分。在这种情况下，子网掩码将由28个前导1和4个0组成，ID为1的子网的地址将指定为204.152.189.16/28。

58.4.2 IPv6地址

　　IPv6的原理类似于IPv4。主要区别在于IPv6地址由128位组成，地址的前几位是格式前缀，表示地址类型 (见RFC 3513)。

　　IPv6地址通常包含多个连续的0，为了方便表示，可以使用双冒号::来表示这样的序列。因此，该地址可以重写为F000::A:1。

　　IPv6地址中只能出现1次双冒号，因为出现多次会导致歧义。

　　IPv6也提供IPv4的环回地址 (127个0后跟1个1，即::1) 和通配地址 (全为0，即0::0或::) 的等效地址。

　　为了使IPv6应用程序与仅支持IPv4的主机通信，IPv6提供了IPv4映射IPv6地址。

　　当书写IPv4映射IPv6地址时，IPv4地址部分采用IPv4点分十进制表示法 (204.152.189.116的IPv4映射IPv6地址是::FFFF:204.152.189.116)。

58.5 传输层

　　传输层的任务是为位于不同或同一主机的应用程序提供端到端通信服务。为此，传输层提供了区分主机上的不同应用程序的方法。对于UDP和TCP，这种区分是通过16位端口号来实现的。

　　一些知名端口会被永久分配给特定应用程序 (也称为服务)。知名端口由互联网号码分配机构 (IANA) 分配，范围是0到1023。知名端口号的分配取决于已批准的网络规范 (通常以RFC的形式)。

　　IANA还会分配已注册端口号，这些端口会以较宽松的方式分配给应用程序开发人员，这表示应用程序无需保证这些端口用于其注册用途。已注册端口的范围是1024到41951 (并非该范围内的所有端口号都已被注册)。

　　对于大多数TCP/IP实现 (包括Linux)，端口号0~1023也是特权端口号 (也称为保留端口号)。绑定这些端口号需要特权 (能力CAP_NET_BIND_SERVICE) 。这可以防止普通用户实现恶意程序 (例如，伪装成ssh) 来获取密码。

　　尽管相同的TCP和UDP端口号是不同的实体，但通常会将知名端口号分配给TCP和UDP的同一项服务 (即使该服务实际上通常只在其中的1个协议下可用)。这种做法可以避免2个协议之间端口号的混淆。

　　若应用程序未将其套接字绑定到某个端口号，则UDP和TCP会为该套接字分配临时端口。在这种情况下，应用程序通常是客户端，它不在意使用的端口号，但分配端口号是必要的，以便传输层协议识别通信端点。此外，这也能使对等应用程序知道如何与该应用程序通信。当将套接字绑定到端口号0时，UDP和TCP也会分配临时端口号。

　　IANA将49152~65535范围内的端口指定为动态端口或私有端口，其目的是让本地应用程序能够使用这些端口，并将其分配为临时端口。但是，不同的实现会从不同的端口范围内分配临时端口。对于Linux，临时端口的范围由文件/proc/sys/net/ipv4/ip_local_port_range中的2个数字定义 (可以通过该文件修改临时端口的范围)。

58.5.1 UDP

　　UDP为IP添加了2个特性：端口号和用于检测传输数据中的错误的数据校验和。

　　与IP相同，UDP也是无连接的。因为UDP没有为IP添加可靠性，所以UDP也是不可靠的。若基于UDP的应用程序需要可靠性，则可靠性必须由应用程序本身提供。

　　UDP和TCP使用的校验和都是16位，并且只是简单的 "累加" 校验和，所以可能无法检测特定类型的错误。因此，它们提供的错误检测并不全面。繁忙的互联网服务器通常每隔几天就会出现1次未被检测到的传输错误。需要更强的数据完整性保证的应用程序可以使用安全套接字层 (SSL)，SSL不仅提供了安全通信，还提供了更全面的错误检测。或者，应用程序可以实现自己的错误检测方案。

　　TCP提供了避免IP分片的机制，而UDP没有提供。当使用UDP传输大于本地数据链路MTU的数据报时，很容易导致IP分片。

　　基于UDP的应用程序通常不知道源主机到目的主机的MTU。为了避免IP分片，此类应用程序通常会使用比较保守的方法：确保传输的IP数据报不大于IPv4最小重组缓冲区的大小576字节，该值通常小于路径MTU。对于这576字节，UDP首部需要8字节，IP首部至少需要20字节，所以UDP有效载荷最大为548字节 (实际上，很多基于UDP的应用程序会选择将其数据报有效载荷限制在512字节)。

58.5.2 TCP

　　TCP在2个端口 (应用程序) 之间提供了可靠的面向连接的双向字节流通信通道。TCP执行了很多任务来实现这一点。

　　这里会使用术语TCP端点来表示内核为TCP连接的一端维护的信息 (包括连接端的发送和接收缓冲区以及为同步已连接端点的操作而维护的状态信息)。在后续的内容中，将使用术语接收端和发送端来表示为流套接字连接两端的接收和发送应用程序维护的TCP端点 (该连接用于沿特定方向传输数据)。

　　在通信开始之前，TCP会在2个端点之间建立通信通道。在建立连接期间，发送端和接收端可以交换选项，以通告连接的相关参数。

　　TCP会将数据拆分为报文段，每个报文段包含校验和，以便检测端到端的传输错误。每个报文段均在独立IP数据报中传输。

58.5.2.1 确认、重传和超时

　　若报文段准确无误地到达，则接收端会发送肯定确认给发送端以告知报文段已成功到达。若收到的报文段包含错误，则该报文段会被丢弃，并且接收端不会发送确认。为了应对报文段无法达到或被丢弃的情况，每当发送端发送报文段时，它会启动1个重传定时器。若重传定时器在收到确认之前过期，则发送端会重传该报文段。

　　传输报文段和接收其确认信息所需的时间因网络范围和当前流量负载而异，所以TCP采用了算法来动态调整重传超时 (RTO) 的时长。

　　接收端可能不会立即发送确认，而是等待一小段时间，以确认能否将确认信息捎带在接收端直接发回给发送端的任何响应报文段的确认字段中。该技术称为延迟确认，旨在减少发送的报文段数，从而降低发送端和接收端的负载。

58.5.2.2 序列号和流量控制

　　TCP连接中传输的每个字节会被分配1个逻辑序列号。这个序列号表示该字节在连接数据流中的位置。连接中的2个数据流各自拥有自己的序列号。报文段的序列号字段包含该报文段的第1个字节的序列号 (序列号是32位值，并且会在达到最大值时回到0)。

　　TCP报文段的序列号字段具有多种用途：

　　● 序列号使得报文段能够在目的端按正确的顺序组装，然后作为字节流传递给应用层 (在任何时刻，发送端和接收端之间都可能同时传输多个报文段，这些报文段到达的顺序可能不同于发送顺序)。

　　● 接收端发回给发送端的确认信息可以利用序列号来标识接收到的报文段。

　　● 接收端可通过序列号来剔除重复的报文段。这类重复可能是由于IP数据报的重复或TCP重传算法认为某个已成功到达的报文段丢失或未按时到达。

　　流的初始序列号 (ISN) 并非从0开始。相反，它是通过算法生成，该算法会递增分配给后续TCP连接的ISN (旨在防止连接的旧实例的报文段被视为当前连接的报文段)。该算法的设计也使得预测ISN变得困难。

　　流量控制可以防止发送速率较快的发送端使接收速率较慢的接收端过载。为了实现流量控制，接收端会维护用于存储传入数据的缓冲区 (TCP会在建立连接时通告该缓冲区的大小)。收到的来自发送端的数据会累积在该缓冲区中，并在应用程序读取数据时被删除。每当发送确认时，接收端会告知发送端其传入缓冲区的可用空间 (发送端可以发送的字节数)。

　　TCP流量控制算法采用滑动窗口算法，该算法允许包含最多N字节 (提供的窗口大小) 的未确认报文段在发送端和接收端之间传输。若接收端的传入数据缓冲区已满，则窗口将关闭，并且发送端停止发送。

　　接收端可以通过套接字选项SO_RCVBUF来覆盖传入数据缓冲区的默认大小。

58.5.2.3 拥塞控制算法：慢启动和拥塞避免算法

　　TCP的拥塞控制算法旨在防止发送速率较快的发送端导致网络过载。若发送端的发送速率高于中间路由器转发分组的速率，则该路由器会开始丢弃分组。若发送端继续以同样的速率重传这些被丢弃的分组，则可能导致高丢包率，进而导致性能严重下降。TCP拥塞控制算法在以下2种情况至关重要：

　　● 当建立连接后或空闲一段时间的连接恢复传输时，发送端可能立即向网络中注入尽可能多的报文段，其数量取决于接收端通告的窗口大小 (实际上，早期TCP实现就是如此)。若网络无法处理如此大量的报文段，则发送端可能立即导致网络过载。

　　● 当发送端检测到拥塞时，它必须调整发送速率。TCP基于假设 "因传输错误而导致的报文段丢失率极低" 检测拥塞的发生，所以一旦分组丢失，便假定其原因是拥塞。

　　TCP拥塞控制算法结合使用了2种算法：慢启动和拥塞避免。

　　慢启动算法会导致发送端最初以较慢的速率发送报文段，但当接收端确认这些报文段后，该算法允许发送速率以指数级增长。慢启动旨在防止发送速率较快的发送端导致网络过载。但是，若不加限制，慢启动过程中发送速率的指数级增长可能会导致网络过载。拥塞控制算法通过对速率增长施加控制，从而避免这一问题。

　　在拥塞避免机制下，当连接建立时，发送端会设置较小的拥塞窗口，以限制其可以发送的未确认数据量。随着发送端收到接收端的确认，拥塞窗口最初呈指数增长。但是，一旦拥塞窗口到达某个被认为接近网络传输容量的阈值，其增长速度将变为线性。网络容量的预估值基于检测到拥塞时实际传输速率计算得出，或者在连接建立时设置为固定值。此外，发送端可传输的数据量始终受限于通告窗口和本地TCP发送缓冲区的大小。

　　慢启动和拥塞避免算法的结合使用允许发送端迅速将发送速率提高到网络可用容量，而不会超过该容量。这些算法的作用是使数据传输能够快速达到平衡状态，即发送端发送分组的速率与收到接收端的确认的速率相同。
