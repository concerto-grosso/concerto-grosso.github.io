《Linux/UNIX系统编程手册》第63章 备选I/O模型

发表于 2026-10-29 更新于 2026-10-31 分类于 Linux 本文字数： 20k

　　本书迄今为止介绍的大部分程序使用的I/O模型都是每个进程每次仅对1个文件描述符执行I/O操作，并且每个I/O系统调用会阻塞进程，直到数据传输完成 (例如，若无名管道中没有数据，则read()通常会阻塞进程；若无名管道中没有足够的空间，则write()通常会阻塞进程。其他类型的文件也会出现类似的行为)。

　　磁盘文件是特例。由于内核会使用缓冲区缓存来加速磁盘I/O请求，所以只要请求的数据被传输到内核缓冲区缓存，对磁盘的write()调用就会返回，而不会等待数据被写入到磁盘 (除非打开文件时指定了标志O_SYNC)。同样，read()会从内核缓冲区缓存读取数据到用户缓冲区，若内核缓冲区缓存没有所请求的数据，则内核会在执行磁盘读取时挂起进程。

　　传统阻塞I/O模型适用于大多数应用程序，但并非适用于所有应用程序。特别是，那些需要执行以下任务中的1项或2项的应用程序：

　　● 以非阻塞模式检查是否可以对文件描述符执行I/O。

　　● 监控多个文件描述符，以检查是否可以对其中的任何1个执行I/O操作。

　　之前已经介绍了能够满足部分需求的技术：非阻塞I/O和多进程或多线程。

　　非阻塞I/O可用于定期检查 (轮询) 文件描述符的I/O是否可用。若需要监控多个文件描述符，则需要让它们进入非阻塞模式，并依次轮询。但是，通过这种方式实现轮询通常不可取。若轮询频率较低，则应用程序响应I/O事件的延迟可能很高。若轮询频率较高，则可能浪费CPU时间。

　　或者，创建子进程来执行I/O。父进程继续执行其他任务，而子进程会被阻塞，直到I/O完成。当需要对多个文件描述符执行I/O时，可以为每个文件描述符创建1个子进程。这种方法的问题是开销大且复杂。创建和维护进程会给系统带来负担，并且子进程通常需要某种IPC机制来通知父进程I/O操作的状态。

　　使用多线程可以降低资源开销，线程之间可能仍然需要交换关于I/O操作状态的信息。当需要使用线程池来最小化能够同时处理大量客户端所需的线程数时，情况可能会变得比较复杂。对于那些调用会执行阻塞I/O的第三方库函数的应用程序，多线程会很有用，应用程序可以在独立的线程调用这些函数来避免被阻塞。

　　由于非阻塞I/O和使用多线程或多进程都存在局限性，通常更推荐使用以下备选方案之一：

　　● I/O多路复用允许进程同时监控多个文件描述符，以确定是否可以对其中的任何1个执行I/O操作。系统调用select()和poll()会执行I/O多路复用。这2个系统调用是UNIX系统中存在已久的接口。

　　● 信号驱动I/O允许进程请求内核在输入可用或可以对指定文件描述符执行写入操作时向其发送信号。进程可以继续执行其他任务，并且会在I/O就绪时收到作为通知的信号。当监控大量文件描述符时，这种方案的性能远优于I/O多路复用。

　　● Linux特有的epoll API最早出现在Linux 2.6中，它允许进程同时监控多个文件描述符，以确定是否可以对其中的任何1个执行I/O操作，并且其性能远优于I/O多路复用。某些UNIX实现提供了类似于epoll API的非标准机制 (例如，Solaris的特殊文件/dev/poll和部分BSD实现的kqueue API)。

　　对于这些技术，文件描述符进入就绪状态是由某个I/O事件触发的 (例如，输入可用、套接字连接的建立或当TCP将排队的数据发送给对端后，之前已满的套接字发送缓冲区有空间可用)。这些技术只是通知进程某个文件描述符进入就绪状态，它们并不会执行I/O。

　　select()和poll()的可移植性更好，而信号驱动I/O和epoll的性能更好。因此，对于某些应用程序，编写用于监控文件描述符事件的抽象软件层是值得的。有了这层抽象，可移植程序可以在支持epoll (或类似API) 的系统上利用该技术，而在其他系统上则回退使用select()和poll()。

　　库libevent是提供文件描述符事件抽象的软件层。它已被移植到很多UNIX系统上。作为底层机制，libevent可以透明地使用本章介绍的所有备选I/O模型：select()、poll()、信号驱动I/O、epoll、Solaris的文件/dev/poll以及BSD实现的kqueue API。

　　文件描述符的就绪通知模型分为2种：水平触发通知和边沿触发通知。

　　● 对于水平触发通知，若对文件描述符执行I/O系统调用不会阻塞进程，则认为该文件描述符处于就绪状态。

　　● 对于边沿触发通知，若文件描述符自上次被监控以来出现了I/O活动 (例如，有新的输入)，则会进行通知。

　　下表总结了I/O多路复用、信号驱动I/O和epoll API的通知模型：

select()和poll()✓
信号驱动I/O✓
epoll API✓✓

　　epoll API既支持水平触发通知 (默认模式)，也支持边沿触发通知。

　　水平触发通知允许在任何时候重复监控I/O，所以每当收到文件描述符就绪的通知时，无需对该文件描述符执行尽可能多的I/O操作，甚至无需立即执行I/O操作。

　　相比之下，当使用边沿触发通知时，只会在I/O事件发生时收到通知，并且在下一次I/O事件发生之前不会收到进一步的通知。此外，当收到某个文件描述符的I/O事件通知时，通常无法得知可以进行多少I/O。因此，使用边沿触发通知的程序的设计通常遵循以下规则：

　　● 当收到I/O事件的通知后，程序应该在某个时刻对对应文件描述符执行尽可能的I/O操作。若程序未能做到这一点，则它可能会错过执行某些I/O的机会，因为它在下一次发生I/O事件之前不会意识到需要对该文件描述符执行操作。这可能导致程序出现虚假的数据丢失或阻塞进程的情况。之所以说是 "某个时刻"，是因为有时在确定文件描述符就绪后，并不一定适合立即执行所有I/O操作。问题在于，对某个文件描述符执行大量I/O操作可能导致其他文件描述符因得不到处理而进入饥饿状态。

　　● 若程序使用循环对某个处于阻塞模式的文件描述符尽可能多地执行I/O操作，则当无法继续执行I/O时，某个I/O系统调用最终会阻塞进程。因此，所有被监控的文件描述符通常被设置为非阻塞模式。当收到I/O事件通知后，程序会反复执行I/O操作，直到相关系统调用导致错误EAGAIN或EWOULDBLOCK。

　　非阻塞I/O (标志O_NONBLOCK) 通常与这3种备选I/O模型一起使用，其使用场景的部分示例如下：

　　● 如前所述，非阻塞I/O通常与使用边沿触发通知的I/O模型一起使用。

　　● 若多个进程 (或线程) 对1组相同的文件描述执行I/O，则从特定进程的角度，文件描述符的就绪状态可能在收到就绪通知与随后执行I/O调用之间发生变化。因此，阻塞I/O调用可能阻塞进程，从而阻止该进程监控其他文件描述符 (无论使用水平触发通知还是边沿触发通知，这3种备选I/O模型都可能出现这种情况)。

　　● 即使在select()和poll()等水平触发API通知进程流套接字的文件描述符可写之后，若该进程试图在单次write()或send()调用写入足够大的数据块，则该调用仍然可能阻塞该进程。

　　● 在极少数情况下，select()和poll()等水平触发API可能返回虚假就绪通知。这种情况可能是内核缺陷导致的，也可能是某个罕见场景下的预期行为 (若客户端连接到服务器的套接字并重置了连接，则在这2个事件之间服务器执行的select()调用可能会指示监听套接字可读，但在客户端重置连接之后的accept()调用会阻塞进程)。

　　POSIX异步I/O (AIO) 允许进程的文件I/O操作排队，并在操作完成时收到通知。它的优势是最早的I/O调用会立即返回，这样进程就不会因等待数据被传输到内核或操作完成而被阻塞。这使得进程能够在执行I/O操作时处理其他任务 (这可能包括让更多的I/O操作排队)。对于某些类型的应用程序，POSIX AIO能带来显著的性能提升。目前，Linux在glibc中提供了基于线程的POSIX AIO实现 (在撰写本书时，相关开发正在进行中，旨在提供内核级的POSIX AIO实现，这应该能提供更好的可扩展性)。

63.1 I/O多路复用

　　系统调用select()与BSD中的套接字API一同出现。系统调用poll()源于System V。从历史角度，前者的应用更广泛。如今，SUSv3要求实现同时支持这2个系统调用。

　　select()和poll()可用于监控常规文件、终端、伪终端、无名管道、有名管道以及部分类型的字符设备的文件描述符。这2个系统调用都可能会无期限地阻塞调用进程，直到文件描述符就绪或超时。

63.1.1 select()

　　系统调用select()会阻塞调用进程，直到1组文件描述符中的至少1个准备就绪。

　　参数readfds、writefds和exceptfds指定待监控的文件描述符。参数timeout指定阻塞时间的上限。

　　这里引用头文件sys/time.h是因为SUSv2详细说明了该头文件，而且有些UNIX实现需要引用该头文件 (Linux提供了该头文件，并且引用该头文件不会导致问题)。

63.1.1.1 文件描述符集

　　参数readfds、writefds和exceptfds是指向数据类型为fd_set的文件描述符集的指针，它们的用法如下：

　　● readfds指向用于监控输入是否就绪的文件描述符集。

　　● writefds指向用于监控输出是否就绪的文件描述符集。

　　● exceptfds指向用于监控是否触发异常条件的文件描述符集。

　　这里的 "异常条件" 并非文件描述符出错。对于Linux，触发异常条件的情况只有少数几种，包括以下情况 (有些UNIX实现与之类似)：

　　● 连接到处于分组模式的主设备的伪终端从设备的状态发生变化。

　　● 接收TCP套接字的带外数据。

　　当无需监控特定类型的事件时，可以将对应的文件描述符集参数指定为NULL。

　　实际上，数据类型fd_set被实现为位掩码。但是，这里不介绍细节，因为对文件描述符集的所有操作都是通过宏FD_ZERO、FD_SET()、FD_CLR()和FD_ISSET()完成的。

　　这4个宏的功能如下：

　　● FD_ZERO()会将fdset指向的文件描述符集初始化为空。

　　● FD_SET()会将文件描述符fd添加到fdset指向的文件描述符集中。

　　● FD_CLR()会从fdset指向的文件描述符集中删除文件描述符fd。

　　● FD_ISSET()会判断文件描述符fd是否为fdset指向的文件描述符集的成员。

　　常量FD_SETSIZE定义了文件描述符集的最大大小，Linux将其定义为1024 (某些UNIX实现将其定义为类似的值)。尽管宏FD_*操作的是用户空间数据结构，并且内核实现的select()可以处理更大的文件描述符集，但glibc没有提供修改FD_SETSIZE的定义的简便方法。若需要修改该限制，则必须修改glibc头文件中的定义。但是，当需要监控大量文件描述符时，epoll API可能比select()更可取。

　　参数readfds、writefds和exceptfds是值-结果参数。在调用select()之前，这些参数指向的文件描述符集必须被初始化为包含目标文件描述符。select()会修改这些文件描述符集，使其在返回时包含已就绪的文件描述符 (因此，当在循环中重复调用select()时，必须确保重新初始化这些文件描述符集)。在select()返回之后，可以通过FD_ISSET()来检查哪些文件描述符已就绪。

　　参数nfds必须被指定为比这3个文件描述符集中的最大文件描述符编号大1。该参数用于提升select()的性能，因为内核后续无需检查大于该值的文件描述符编号是否属于这些文件描述符集。

63.1.1.2 参数timeout

　　参数timeout用于控制select()的阻塞时间，可以将其指定为NULL表示select()会无期限地阻塞进程。若该参数指向的结构体timeval的成员都被指定为0，则select()不会阻塞进程。

　　尽管结构体timeval提供了微秒级精度，但select()的超时时间的精度受限于软件时钟粒度 (SUSv3要求超时时间不是该粒度的整数倍时向上取整)。

　　SUSv3要求超时时间上限至少为31天。大多数UNIX实现允许的上限要高得多，Linux/x86-32的上限长达数年 (因为使用32位整数来表示数据类型time_t)。

　　当timeout为NULL或它指向的结构体timeval的成员不都为0，则select()会阻塞进程，直到发生以下事件之一：

　　● readfds、writefds和exceptfds指定的文件描述符中至少有1个变为就绪状态。

　　● 该调用被信号处理函数中断。

　　● timeout指定的时间已过。

　　对于缺乏nanosleep()等具有亚秒级精度休眠调用的早期UNIX实现，select()可用于模拟该功能：将nfds指定为0，将readfds、writefds和exceptfds都指定为NULL，并且将timeout指定所需的休眠时间间隔。

　　对于Linux，若select()因文件描述符就绪而返回，并且timeout不为NULL，则它会更新timeout指向的结构体，以反映距离调用超时还有多少时间。但是，这种行为是实现特有的。SUSv3也允许实现不修改该结构体，并且大多数UNIX实现也不会修改该结构体。可移植应用程序应该确保每次调用select()之前初始化timeout指向的结构体，并忽略调用后该结构体中返回的信息。

　　SUSv3规定，当且仅当select()成功时，timeout指向的结构体才会被修改。但是，对于Linux，若select()被信号处理函数中断 (导致错误EINTR)，该结构体也会被修改，以反映距离调用超时还有多少时间。若使用Linux特有的系统调用personality()设置包含特征标志STICKY_TIMEOUTS的特征，则select()不会修改timeout指向的结构体。

63.1.1.3 select()的返回值

　　select()会返回以下值之一：

　　● 返回值-1表示出错。可能的错误包括EBADF和EINTR。前者表示readfds、writefds和exceptfds指定的文件描述符包含无效文件描述符 (例如，当前未被打开)，后者表示select()被信号处理函数中断 (如前所述，该系统调用在这种情况下永远不会自动重启)。

　　● 返回值0表示超时。在这种情况下，所有返回的文件描述符集都为空。

　　● 正返回值表示文件描述符就绪，返回值是就绪的文件描述符数。在这种情况下，必须检查所有返回的文件描述符集 (使用FD_ISSET()) 来确定发生了哪些I/O事件。若某个文件描述符在readfds、writefds和exceptfds指定的文件描述符集中出现多次，并且该文件描述符处于多个事件的就绪状态，则它会被多次计数 (select()的返回值是这3个文件描述符集中所有处于就绪状态的文件描述符的总数)。

63.1.2 poll()

　　系统调用poll()会执行与select()类似的任务，但它使用不同的方式来指定待监控的文件描述符。数组fds指定待监控的文件描述符，其元素数由参数nfds指定 (数据类型nfds_t是无符号整数类型)。参数timeout指定超时时间。

63.1.2.1 结构体pollfd

　　● 标志POLLRDBAND通常不会被使用，该标志仅在实现已过时的DECnet网络协议的代码中被设置。

　　● 尽管在特定情况下套接字会设置标志POLLWRBAND，但它并不会传达任何有效信息 (不存在POLLWRBAND被设置而POLLOUT和POLLWRNORM未被设置的情况)。

　　● 当定义了特性测试宏_XOPEN_SOURCE后，标志POLLRDNORM、POLLRDBAND、POLLWRNORM和POLLWRBAND的定义才会出现在头文件poll.h中。

　　● Linux特有的标志POLLRDHUP最早出现在内核2.6.17中。当定义了特性测试宏_GNU_SOURCE，该标志的定义才会出现在头文件poll.h中。

　　● 若调用poll()时文件描述符已被关闭，则标志POLLNVAL会被设置。

　　● 对于提供了STREAMS设备的UNIX实现，标志POLLMSG表示包含信号SIGPOLL的信息已到达流首部。Linux未使用该标志，因为Linux没有实现STREAMS。

63.1.2.2 参数timeout

　　参数timeout决定poll()的阻塞行为。

　　● 若该参数为-1，则该系统调用会阻塞调用进程，直到数组fds中至少有1个文件描述符就绪或捕获到信号。

　　● 若该参数为0，则该系统调用会以非阻塞模式检查文件描述符是否就绪。

　　● 若该参数大于0，则该系统调用会阻塞调用进程最多timeout毫秒，直到数组fds中至少有1个文件描述符就绪或捕获到信号。

　　同样，timeout的精度受限于软件时钟粒度 (SUSv3要求该参数不是软件时钟粒度的整数倍时向上取整)。

63.1.2.3 poll()的返回值

　　poll()会返回以下值之一：

　　● 返回值-1表示出错。EINTR是可能的错误之一，表示被信号处理函数中断 (如前所述，该系统调用在这种情况下永远不会自动重启)。

　　● 返回值0表示超时。

　　● 正返回值表示文件描述符就绪，返回值是数组fds中成员revents非0的元素的数量 (即使成员revents中的多个位被设置，对应的文件描述符也只会被计数1次)。

63.1.4 select()和poll()的比较

63.1.4.1 实现细节

　　在Linux内核中，select()和poll()都使用同一组内核内部的poll例程。这些poll例程不同于poll()。每个例程会返回单个文件描述符的就绪相关信息。这些就绪信息采用位掩码的形式，其值对应poll()在revents中设置的标志。poll()的实现涉及为每个文件描述符调用内核poll例程，并根据结果信息设置revents中的标志。

63.1.4.2 API差异

　　select()和poll()存在以下差异：

　　● select()可以监控的文件描述符数受限于数据类型fd_set的上限FD_SETSIZE。对于Linux，该限制默认是1024，修改它需要重新编译应用程序。相比之下，poll()没有对可以监控的文件描述符数设置上限。

　　● select()的fd_set参数是值-结果参数，所以在循环中重复调用select()时必须重新初始化这些参数。通过将输入事件 (events) 和输出事件 (revents) 分离，poll()避免了这一要求。

　　● select()的超时精度 (微秒) 大于poll()的超时精度 (毫秒)，但它们的超时精度都受限于软件时钟粒度。

　　● 当被监控的文件描述符被关闭时，poll()会通过设置对应revents中的标志POLLNVAL来表示具体的文件描述符。相比之下，select()只会出错 (EBADF)。 但是，该差异通常不重要，因为应用程序通常可以追踪它关闭了哪些文件描述符。

63.1.4.3 可移植性

　　从历史角度，select()比poll()更普及。如今，它们都已由SUSv3标准化，并且在现代实现中广泛可用。但是，不同实现的poll()的行为存在一些差异。

63.1.4.4 性能

　　当满足以下任一条件时，select()和poll()的性能类似：

　　● 监控的文件描述符范围较小 (最大文件描述符编号较小)。

　　● 监控大量编号几乎连续的文件描述符。

　　若在指定范围内仅有少数几个文件描述符被监控，则poll()的性能可能远优于select() (对于Linux 2.4，这种性能差距相当显著。Linux 2.6的某些优化措施已经大大缩小了这一性能差距)。

　　对于select()，参数nfds比被监控的最大文件描述符编号大1，内核必须检查nfds个元素来确定哪些文件描述符正在被监控。相比之下，poll()可以仅指定待监控的文件描述符，并且内核只会检查这些文件描述符。

63.1.5 select()和poll()的问题

　　当使用select()和poll()监控大量文件描述符时，存在以下问题：

　　● 每次调用select()和poll()时，内核必须检查所有的文件描述符来确定它们是否就绪。当监控大量位于密集范围内的文件描述符时，该操作所需的时间远超后续2项操作所需的时间。

　　● 当调用select()和poll()时，程序必须向内核传递用于描述所有待监控的文件描述符的数据结构，并在调用后检查文件描述符 (对于select()，每次调用前需要初始化该数据结构)，内核会将修改后的数据结构返回给程序。对于poll()，该数据结构的大小随着被监控的文件描述符数增加而增加。当监控大量文件描述符时，将该数据结构从用户空间复制到内核空间以及从内核空间复制回用户空间需要大量CPU时间。对于select()，该数据结构的大小固定为FD_SETSIZE。

　　● 当调用select()和poll()后，程序必须检查返回的数据结构的所有元素来确定就绪的文件描述符。

　　以上几点会导致select()和poll()所需的CPU时间随着被监控的文件描述符数增加而增加。

　　select()和poll()的可扩展性较差，因为程序通常会调用它们来反复监控同一组文件描述符，但内核不会在连续调用时记住被监控的文件描述符。

63.2 信号驱动I/O

　　对于I/O多路复用，进程会通过系统调用来检查文件描述符的I/O是否可用。对于信号驱动I/O，进程会请求内核在文件描述符的I/O可用时向其发送信号。为了使用信号驱动I/O，程序会执行以下操作：

　　1) 为信号驱动I/O机制发送的信号 (默认是SIGIO) 注册信号处理函数。

　　2) 设置文件描述符的所有者，即该文件描述符的I/O可用时接收信号的进程或进程组。可以通过fcntl()的操作F_SETOWN来设置所有者：

63.2.1 作为I/O就绪通知的信号的生成时间

63.2.1.1 终端和伪终端

　　对于终端和伪终端，当新输入可用时，信号会被生成 (即使存在未被读取的输入)。当终端触发EOF条件时，信号也会被生成。

　　对于终端，当输出可用和断开连接时，信号不会被生成。

　　从Linux 2.4.19开始，当伪终端的主设备消耗输入时，内核会为对应的伪终端的从设备生成信号。

63.2.1.2 无名管道和有名管道

　　对于无名管道和有名管道的读取端，当出现以下情况时，信号会被生成：

　　● 数据被写入到管道 (即使存在未被读取的输入)。

　　● 管道的写入端被关闭。

　　对于无名管道和有名管道的写入端，当出现以下情况时，信号会被生成：

　　● 管道中有足够的空间来以非阻塞方式写入PIPE_BUF字节。

　　● 管道的读取端被关闭。

63.2.1.3 套接字

　　对于UNIX域和互联网域数据报套接字，当出现以下情况时，信号会被生成：

　　● 输入数据报到达套接字 (即使存在未被读取的数据报)。

　　● 套接字发生异步错误。

　　对于UNIX域和互联网域流套接字，当出现以下情况时，信号会被生成：

　　● 监听套接字接受新连接。

　　● TCP的connect()请求完成，执行主动打开的端点进入状态ESTABLISHED。

　　● 套接字上的新输入被接收 (即使存在未被读取的输入)。

　　● 对端通过shutdown()关闭其写入通道或通过close()关闭其套接字。

　　● 套接字上的输出可用 (例如，套接字发送缓冲区有足够空间)。

　　● 套接字发生异步错误。

63.2.1.4 inotify文件描述符

　　当inotify文件描述符可读时 (即inotify文件描述符监控的文件发生事件)，信号会被生成。

63.2.2 优化信号驱动I/O的使用

　　当需要同时监控大量文件描述符时，相比select()和poll()，信号驱动I/O可以带来显著的性能优势，因为内核会记录被监控的文件描述符，并且仅在这些文件描述符上实际发生I/O事件时才向程序发送信号。因此，使用信号驱动I/O的程序的性能会随着I/O发生的数量而相应变化 (而非被监控的文件描述符数)。

　　为了充分利用信号驱动I/O优势，必须执行以下步骤：

　　1) 使用Linux特有的fcntl()操作F_SETSIG来指定实时信号作为文件描述符上的I/O就绪通知。

　　2) 当通过sigaction()为上一步指定的实时信号注册处理函数时，指定标志SA_SIGINFO。

63.2.2.1 处理信号队列溢出

　　可以排队的实时信号存在上限。若达到该上限，则内核会将作为I/O就绪通知的信号重置为SIGIO。当发生这种情况时，关于哪些文件描述符上发生I/O事件的信息会丢失 (信号SIGIO不会排队)。此外，SIGIO处理函数只有1个参数，所以该处理函数无法确定发生了I/O事件的文件描述符。

　　可以通过增加实时信号队列的上限来降低实时信号队列溢出的可能性，但这无法消除这种可能性。因此，使用信号驱动I/O的应用程序也应该注册SIGIO处理函数。当收到信号SIGIO时，应用程序可以通过sigwaitinfo()清空实时信号队列，并临时使用select()或poll()获取包含待处理I/O事件的文件描述符的完整列表。

63.2.2.2 在多线程应用程序中使用信号驱动I/O

　　从内核2.6.32开始，Linux提供了非标准fcntl()操作F_SETOWN_EX和F_GETOWN_EX。

　　操作F_SETOWN_EX与F_SETOWN类似，但允许进程、进程组或线程作为I/O就绪通知的目标。为此，fcntl()的第3个参数必须是指向结构体f_owner_ex的指针：

　　成员type决定成员pid的含义，可以被指定为F_OWNER_PGRP、F_OWNER_PID或F_OWNER_TID。

　　● 当type为F_OWNER_PGRP时，pid用于指定作为I/O就绪通知目标的进程组的ID。不同于F_SETOWN，这里的进程组ID应该被指定为正值。

　　● 当type为F_OWNER_PID时，pid用于指定作为I/O就绪通知目标的进程的进程ID。

　　● 当type为F_OWNER_TID时，pid用于指定作为I/O就绪通知目标的线程的线程ID (clone()和gettid()的返回值)。

　　操作F_GETOWN_EX会与F_SETOWN_EX相反，它会使用fcntl()的第3个参数指向的结构体f_owner_ex返回上一个F_SETOWN_EX操作指定的设置。

63.3 epoll API

　　epoll (event poll) API是Linux特有的，添加于Linux 2.6。

　　epoll API的核心数据结构是epoll实例，它由打开的文件描述符引用。该文件描述符不会用于I/O，相反，它是内核数据结构的句柄，而该数据结构有2个用途：

　　● 记录进程希望监控的文件描述符列表——监控列表。

　　● 维护I/O就绪的文件描述符列表——就绪列表 (监控列表的子集)。

　　对于epoll监控的每个文件描述符，进程可以指定表示目标事件的位掩码 (与poll()使用的位掩码极其相似)。

　　epoll API主要由系统调用epoll_create()、epoll_ctl()和epoll_wait()组成。

　　● epoll_create()会创建1个epoll实例并返回引用该实例的文件描述符。

　　● epoll_ctl()用于操作与epoll实例关联的监控列表。

　　● epoll_wait()会返回与epoll实例关联的就绪列表中的条目。

63.3.1 epoll_create()

　　系统调用epoll_create()会创建监控列表为空的epoll实例。

　　参数size用于指定希望通过epoll实例监控的文件描述符数。该参数不是上限，只是提供给内核的关于如何初始化内部数据结构的提示。从Linux 2.6.8开始，该参数必须大于0，但除此之外将被忽略，因为实现的修改导致内核不再需要该参数提供的信息。

　　该系统调用会返回引用新epoll实例的文件描述符 (用于其他epoll系统调用)。当不再需要该文件描述符时，应通过close()关闭它。当所有引用epoll实例的文件描述符都被关闭后，该实例会被销毁，相关资源也会被释放。

　　当进程调用epoll_create()时，内核在内存中创建1个i-node以及打开的文件描述，并为调用进程分配1个引用该打开的文件描述的文件描述符。epoll实例的监控列表关联的是打开的文件描述，而非epoll文件描述符。

　　当使用dup() (或类似的系统调用) 复制epoll文件描述符时，复制的文件描述符会引用相同的epoll实例和监控列表。因此，可以对其中的任一文件描述符调用epoll_ctl()来修改监控列表。同样，也可以对其中的任一文件描述符调用epoll_wait()来检索监控列表中的就绪文件描述符的相关信息。这同样适用于fork()，子进程会继承父进程的epoll文件描述符 (引用相同的epoll数据结构)。

　　从内核2.6.27开始，Linux提供了与epoll_create()类似的系统调用epoll_create1()。它将过时的参数size替换为用于控制其行为的参数flags。flags目前仅支持标志EPOLL_CLOEXEC，该标志会让内核启用新文件描述符的close-on-exec标志 (FD_CLOEXEC)。

63.3.2 epoll_ctl()

　　系统调用epoll_ctl()可用于修改文件描述符epfd引用的epoll实例关联的监控列表。

　　参数fd是目标文件描述符，可以是无名管道、有名管道、套接字、POSIX消息队列、inotify实例、终端、设备以及epoll实例的文件描述符，但不能是常规文件或目录的文件描述符 (否则导致错误EPERM)。

　　参数op指定目标操作，可以被指定为EPOLL_CTL_ADD、EPOLL_CTL_MOD或EPOLL_CTL_DEL。

　　● EPOLL_CTL_ADD表示将fd添加到epfd的监控列表，待监控的事件通过ev指向的缓冲区指定。当试图向监控列表添加重复的文件描述符时，epoll_ctl()会导致错误EEXIST。

　　● EPOLL_CTL_MOD表示根据ev指向的缓冲区中的信息更新fd的事件设置。当试图修改不属于监控列表的文件描述符时，epoll_ctl()会导致错误ENOENT。

　　● EPOLL_CTL_DEL表示从epfd的监控列表中删除fd (该操作会忽略ev)。当试图删除不属于监控列表的文件描述符时，epoll_ctl()会导致错误ENOENT。关闭文件描述符会自动将其从其所属的所有监控列表中删除。

　　参数ev指定文件描述符fd的设置。

　　● 子成员events是位掩码，用于指定希望对fd监控的事件。

　　● 子成员data是共用体，其中的1个成员将用于指定fd就绪时传回给调用epoll_wait()的进程的信息。

　　当执行epoll_ctl()的操作EPOLL_CTL_ADD时，内核会在epoll监控列表中添加对应条目 (记录了被监控的文件描述符编号以及对应的打开的文件描述的引用)。为了处理epoll_wait()调用，内核会监控打开的文件描述。

　　这里的epoll_wait()会返回文件描述符fd1就绪 (evlist[0].data.fd等于fd1)，即使它已被关闭。这是因为文件描述符fd2和fd1引用的是同一打开的文件描述，其中包含epoll监控列表。

　　当不同进程有引用同一打开的文件描述的文件描述符时 (通常是fork()调用的结果)，也会出现类似的情况。

　　epoll监控列表中的每个文件描述符需要少量不可交换的内核内存，所以内核提供了用于定义每个用户在所有epoll监控列表中可以注册的文件描述符总数的限制的接口，其值可以通过目录/proc/sys/fs/epoll下的Linux特有文件max_user_watches查看和修改 (默认值是基于系统可用内存计算的)。

63.3.3 epoll_wait()

　　系统调用epoll_wait()会返回文件描述符epfd引用的epoll实例的就绪文件描述符的相关信息，结果会被存储在由结构体epoll_event组成的数组evlist中。该数组由调用者分配，其元素数通过参数maxevents指定。该系统调用可以返回多个就绪文件描述符的相关信息。

　　数组evlist中的每个元素返回单个就绪文件描述符的相关信息。

　　● 对于子成员events，与文件描述符发生的事件对应的标志会被设置。

　　● 子成员data返回通过epoll_ctl()将文件描述符加入监控列表时为ev.data指定的值 (成员data提供了用于获取发生事件的文件描述符的编号的唯一途径。因此，当通过epoll_ctl()将文件描述符添加到监控列表时，应该将ev.data.fd设置为文件描述符编号或将ev.data.ptr设置为指向包含文件描述符编号的结构体的指针)。

　　参数timeout决定epoll_wait()的阻塞行为。

　　● 若timeout为-1，则一直阻塞进程，直到epfd的监控列表中的文件描述符发生事件或捕获到信号。

　　● 若timeout为0，则以非阻塞模式检查epfd的监控列表中的文件描述符是否发生事件。

　　● 若timeout大于0，则阻塞进程最长timeout毫秒，直到epfd的监控列表中的文件描述符发生事件或捕获到信号。

　　epoll_wait()会返回数组evlist的元素数。若阻塞超时，则返回0；若出错，则返回-1并设置errno。

　　对于多线程程序，可以让某个线程通过epoll_ctl()将正在被其他线程通过epoll_wait()监控的文件描述符添加到epoll实例的监控列表。这种修改会立即生效，并且epoll_wait()会返回新添加的文件描述符的就绪信息。

　　● 内核会检查select()或poll()调用指定的所有文件描述符。相比之下，当通过epoll_ctl()将文件描述符标记为待监控时，内核会将该信息记录在与底层打开的文件描述关联的列表中。每次执行使文件描述符就绪的I/O操作时，内核会向epoll文件描述符的就绪列表中添加条目。后续的epoll_wait()调用只需要检索就绪列表中的条目。

　　● 调用select()或poll()需要内核传递用于标识所有待监控的文件描述符的数据结构，并且当调用返回时，内核会返回包含就绪文件描述符相关信息的数据结构。相比之下，当使用epoll时，可以调用epoll_ctl()在内核空间中构建包含待监控的文件描述符集的数据结构。一旦该数据结构构建完成，后续的epoll_wait()调用无需向内核传递任何文件描述符的相关信息，并且该调用只会返回就绪文件描述符的相关信息。

　　此外，对于select()，在调用前必须初始化输入数据结构；对于select()和poll()，必须检查返回的数据结构以确定哪些文件描述符就绪。但是，某些测试表明，与通过这些系统调用监控大量文件描述符相比，这些其他步骤的耗时可以忽略不计 (上表不包含检查步骤的耗时)。

63.3.5 边沿触发通知

　　epoll默认使用水平触发通知，但也支持边沿触发通知。当使用边沿触发通知时，调用epoll_wait()会返回自上一次调用该系统调用以来 (或者若之前没有调用，则自打开文件描述符以来) 文件描述符是否有I/O活动。从语义角度，使用边沿触发通知的epoll类似于信号驱动I/O，区别在于，当发生多个I/O事件时，epoll会将它们合并为1个通知 (通过epoll_wait()返回)，而信号驱动I/O则可能生成多个信号。

　　为了使用边沿触发通知，需要在调用epoll_ctl()时指定标志EPOLLET。

　　这里将通过示例介绍水平触发和边沿触发epoll通知的区别。假设使用epoll监控套接字的输入 (EPOLLIN)：

　　1) 输入到达套接字。

　　2) 调用epoll_wait()，该调用会返回套接字就绪的信息 (无论使用的是水平触发通知还是边沿触发通知)。

　　3) 再次调用epoll_wait()。

　　若使用的是水平触发通知，则第2次epoll_wait()调用会返回套接字就绪。若使用的是边沿触发通知，则第2次epoll_wait()调用会阻塞进程，因为自上一次epoll_wait()调用以来没有新的输入到达。

　　如前所述，边沿触发通知通常与非阻塞文件描述符一起使用，所以使用边沿触发epoll通知的一般框架如下：

　　1) 将所有待监控的文件描述符标记为非阻塞模式。

　　2) 使用epoll_ctl()构建epoll监控列表。

　　3) 循环处理I/O事件。每次循环会通过epoll_wait()检索就绪文件描述符。对于每个就绪文件描述符，处理I/O，直到read()、write()、recv()、send()或accept()等相关系统调用导致错误EAGAIN或EWOULDBLOCK。

　　假设使用边沿触发通知监控大量文件描述符，当就绪文件描述符有大量输入可用时，若检测到该文件描述符就绪后试图以非阻塞方式读取所有输入，则可能导致其他文件描述符得不到及时处理 (即可能需要很长时间才能检查它们是否就绪并对它们执行I/O)。解决方法之一是让应用程序维护已就绪的文件描述符列表，并一直循环执行以下步骤：

　　1) 通过epoll_wait()监控文件描述符并将就绪文件描述符添加到应用程序列表中。若该列表中的文件描述符已被登记为就绪，则应该将监控步骤的超时时间设置为较短的值或0，以便在没有新文件描述符就绪时应用程序可以快速进入下一步并处理任何已知的就绪文件描述符。

　　2) 对应用程序列表中的就绪文件描述符执行有限的I/O (例如，以轮询方式处理它们，而非每次都从列表开头开始)。当相关系统调用导致错误EAGAIN或EWOULDBLOCK时，应该从应用程序列表中删除对应文件描述符。

　　尽管这需要额外的编程工作，但除了能够防止文件描述符饥饿之外，这种方法具有其他优点 (例如，在循环中加入处理定时器或通过sigwaitinfo()接收信号等其他步骤)。

　　当使用信号驱动I/O时，也可能出现类似的饥饿情况。相比之下，水平触发通知不会出现这种饥饿情况，因为水平触发通知可以与阻塞文件描述符一起使用，并使用循环 (每次循环会检查文件描述符是否就绪并对其执行部分I/O)。

63.4.2 self-pipe技巧

　　因为pselect()并未被广泛实现，所以可移植应用程序必须使用其他策略来避免同时调用select()和等待信号时出现的竞争条件。常见的解决方法之一如下：

　　1) 创建无名管道并将其读取端和写入端标记为非阻塞模式。

　　2) 除了监控待监控的文件描述符之外，还应该在select()的readfds中指定无名管道的读取端。

　　3) 为目标信号注册信号处理函数。当信号处理函数被调用时，它会向无名管道写1字节的数据。

　　4) 循环调用select()，以便于它被信号处理函数中断时能够重启。这种重启方式是必要的，它只是意味着可以通过readfds来判断是否收到了信号，而非检查是否导致了错误EINTR。

　　5) 当成功完成select()调用后，通过检查readfds中的无名管道读取端的文件描述符来确定信号是否到达。

　　6) 每当信号到达时，读取无名管道中的所有数据。由于可能有多个信号到达，所以使用循环来读取字节，直到非阻塞的read()调用导致错误EAGAIN。当清空无名管道后，执行接收信号所需的操作。

　　● 第1步将无名管道的写入端标记为非阻塞模式是为了防止信号到达速度过快导致信号处理函数被反复调用而填满无名管道，从而导致信号处理函数的write()调用阻塞进程 (向已满的无名管道写入失败也无关紧要，因为之前的写入操作表明信号已到达)。
